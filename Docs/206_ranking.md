# 206 — 랭킹 & 결과 구현

> 기록 데이터 구조와 랭킹 계산. 소유: 통합 담당 (Result 씬) — 계산 로직은 공유 타입으로.
> 룰 근거: `100_game_design.md` 7장.

## 1. 기록 데이터

```csharp
class PlayerRecord {
    bool Cleared;        // 클리어 여부
    float ClearTime;     // 클리어 시간(초) — 시작부터 골 도달까지
    int AttemptsUsed;    // 사용한 시도 횟수 = 1 + R키 수동 리스폰 횟수 (낙하 자동 리스폰은 미소모)
    bool GaveUp;         // 미클리어 (시도 제한 소진 또는 플레이 시간 만료)
}
```

- 전송/비교에 쓰는 유효 시간: `EffectiveTime`(아래 2장)
- 패타임: 검증 플레이(상대 뜻으로 자기 맵 클리어)의 클리어 시간 — `MatchData.MyParTime` (`201_common.md` 3장)

## 2. 랭킹 공식

### 2.1 기본 모드 (패타임 끔)

```
score = EffectiveTime  →  낮을수록 승
```

### 2.2 패타임 모드 (패타임 켬)

```
score = EffectiveTime / ParTime  →  낮을수록 승
```

- 맵 난이도를 정규화 — 제작자 기준선(패타임) 대비 얼마나 빨리 뛰었는가로 경쟁

### 2.3 EffectiveTime 산출

| 상황 | 값 |
|---|---|
| 클리어 | 실제 클리어 시간 |
| 미클리어 (시도 소진 또는 플레이 시간 만료) | `EffectiveTime = PlayTimeLimit` (모드 무관). 패타임 모드 ON에서는 자동으로 `PlayTimeLimit ÷ ParTime`이 되어 어떤 클리어 기록보다 항상 나쁨 |
| 클리어 불가 (시도 무제한) | 플레이 시간 제한으로 반드시 종료 → 위 미클리어 처리 |

> **클리어는 미클리어를 항상 이긴다** (구현 `Ranking.Judge` 첫 단계). 두 플레이어는 서로 다른 맵(다른 패타임)을 플레이하므로 패타임 모드에서 `PlayTimeLimit ÷ 패타임` 비교만으로는 미클리어가 클리어를 이기는 역전이 생길 수 있어(예: 패타임 100s 맵 기권 = 1.8 vs 패타임 20s 맵 60s 클리어 = 3.0) 점수 비교 전에 클리어 여부를 먼저 판정한다.
>
> ⚠ 변경 제안 (확인 필요): 기존 안 "패타임 모드 ON 시 기권 = 패타임 × 2"는 패타임 30초 맵에서 기권(비율 2.0)이 90초 클리어(비율 3.0)보다 **유리해지는 역전**이 생긴다. 미클리어를 항상 `PlayTimeLimit`으로 두면 클리어 시간은 항상 제한보다 짧으므로 역전이 구조적으로 불가능하다.

### 2.4 동점 처리

1. 유효 점수 동일 → 시도 횟수(`AttemptsUsed`) 적은 쪽 우위 (패타임 합은 양쪽 동일한 값이라 재비교 불가 — 사용 금지)
2. 그래도 동일 → **무승부** 표시

## 3. 승패 구조

| 비교 | 내용 |
|---|---|
| A의 점수 | A가 B가 만든 맵을 A의 뜻으로 클리어한 기록 |
| B의 점수 | B가 A가 만든 맵을 B의 뜻으로 클리어한 기록 |
| 판정 | 점수 낮은 쪽 승 |

- 결과 화면 표시 데이터: 양쪽 클리어 시간, 패타임(모드 ON 시), 승자 — `204_ui.md` 2.4

## 4. 구현 위치

- 계산 로직: 공유 타입 영역(`Scripts/Common/`) — Result 씬에서 호출, 부작용 없는 순수 함수로
- 기록 확정 흐름: Play(로컬 측정) → `PlayerRecord` → 네트워크 전송(`205_network.md` 이벤트 4) → 양쪽 수신 완료 → Result에서 산출
- 방 설정 참조: `MatchData.Settings` (`RoomProperties`에서 로드됨 — `205_network.md` 2장)
